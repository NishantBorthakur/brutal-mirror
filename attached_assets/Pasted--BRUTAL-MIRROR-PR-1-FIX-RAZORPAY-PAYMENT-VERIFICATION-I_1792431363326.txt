## 2. IDENTIFIED VULNERABILITY

The audit found that `/api/billing/verify-payment` checks an order's current status before performing the database transaction that updates the order and grants credits.

The order-status update is not sufficiently conditional on the order still being eligible.

Consequently, concurrent verification requests can both observe the same initial status and independently grant credits.

This can lead to duplicate credit allocation for a single successful payment.

Review the code and verify that the vulnerability is present before implementing the correction.

## 3. REQUIRED IMPLEMENTATION

Introduce robust, database-backed idempotency for payment verification.

The solution must:

### A. Enforce atomic state transitions

Use a database transaction to atomically claim an eligible payment order and grant credits.

Prefer the existing PostgreSQL/Drizzle architecture and a conditional order-status update, row-level locking, or another appropriate concurrency-safe mechanism.

Only one concurrent request should be able to successfully perform the payment order transition that authorizes the credit grant.

Use the actual existing status lifecycle instead of assuming every valid order must transition from a status named `created`.

### B. Prevent duplicate credit grants

For a successfully verified payment:

- Verify the Razorpay signature before granting any credits.
- Confirm payment/order ownership and amount information through the existing validation path.
- Permit exactly one credit allocation for the corresponding paid order.
- Reject or safely handle a mismatched Razorpay payment ID.
- Ensure duplicate requests cannot produce additional credits.
- Ensure duplicate requests cannot produce duplicate purchase transactions.

A repeated legitimate verification should return an appropriate idempotent response without another credit grant.

### C. Preserve transaction integrity

Credit granting, corresponding ledger insertion, and payment order status transition must form one consistent atomic operation.

If the database transaction fails, do not leave behind:

- A verified order without credited balance
- Credited balance without an appropriate ledger record
- A purchase ledger record without the corresponding credit update

The entire operation should commit together or roll back together.

### D. Coordinate with the webhook handler

Inspect the existing `payment.captured` webhook behavior.

Make sure verification requests and webhook delivery cannot independently credit the same order twice.

The verification route and webhook should share a consistent, concurrency-safe credit allocation invariant.

Avoid an unnecessary rewrite of unrelated webhook logic.

Handle duplicate delivery and out-of-order events safely.

### E. Preserve existing user behavior

Do not change:

- The credit pack prices or quantities
- The existing Razorpay provider integration
- The checkout UI
- The user authentication system
- The general payment flow
- The existing successful checkout response format, unless a minimal compatible change is essential
- The credit display functionality
- Unrelated application functionality

Keep the fix focused and compatible with the existing frontend.
